# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is the **development home for an agentic ticket workflow** — a Linear-ticket → GitHub-PR autonomous coding pipeline built entirely from Claude Code subagents, slash commands, a sandbox, and an eval harness. This project directory is just the workspace you operate from; **the system itself lives at user level in `~/.claude/`** and is auto-loaded into every Claude Code session on this machine.

When asked to change "the workflow," "an agent," or "a command," you are editing files under `~/.claude/`, not files in this directory.

**Source of truth:** the agent files (`~/.claude/agents/*.md`) and command files (`~/.claude/commands/*.md`) are self-documenting and define real behavior. The prose docs (`./TICKET-WORKFLOW.md`, `./ticket-workflow.html`, in this project directory) are overviews — when they disagree with the agent/command files, the files win. Read the relevant file before editing; never recreate or contradict the system from memory.

## This repo IS the version-controlled source — `~/.claude/` is a deployed copy

`install.sh` copies **this repo → `~/.claude/`** (one-way: `agents/`, `commands/`, `bin/`, `hooks/`, and the whole `ticket-workflow-evals/`). So:

- The files that **auto-load into every session** and actually run are the ones under `~/.claude/` (the live copy). That's why you edit/operate there.
- The files that are **version-controlled** are the ones in *this* repo. `~/.claude/` is **not** a git repo — changes made there show up in **no** `git status` until you copy them back here.
- **To commit any change that originated in `~/.claude/`, sync it back into this repo's mirror first, then `git add`/commit.** Don't conclude "nothing to commit" from a clean `git status` in this repo alone — check the live copy too (`diff -rq ~/.claude/<dir> ./<dir>`).

**Eval outputs are the common case of this.** `/wf-eval` uses `EVAL=~/.claude/ticket-workflow-evals`, so every run record (`baselines/run-<date>.md`) and any `baseline.md` promotion lands in the **deployed** copy, never here. Committing eval results = `cp ~/.claude/ticket-workflow-evals/baselines/{baseline.md,run-*.md} ./ticket-workflow-evals/baselines/` → commit. (This bit me once: I reported "nothing to commit" because I'd only looked at this repo's clean status.)

## The agents (`~/.claude/agents/`)

**Reasoning agents** — `wf-spec-builder` (opus, interactive: ticket → implementation-ready spec), `wf-planner` (opus: spec → surgical plan + forward Context Pack), `wf-executor` (sonnet: implements plan, atomic commits), `wf-reviewer` (opus: reviews diff coverage-first — reports every finding with a confidence tag; only precisely-routed BLOCKING items drive the fix loop), `wf-verifier` (sonnet: runs tests/build/lint, proves acceptance criteria), `wf-cartographer` (sonnet: one-time, writes a repo's `CONTEXT.md` manual).

**Boundary agents** — each owns *all* I/O to one external system so other agents stay free of API plumbing: `wf-linear` (haiku, all Linear MCP calls), `wf-github` (haiku, all `gh` CLI calls).

**Orchestration agent** — `wf-runner` (sonnet: drives one ticket's execute → review → verify inner loop in its worktree, coordinating executor/reviewer/verifier; `/wf-run`'s single canonical inner loop in both sequential and `--parallel` mode; never touches Linear/GitHub, never asks the user).

**Eval-only** — `wf-judge` (sonnet, LLM-as-judge; used by the eval harness, never in `/wf-run`).

Model tiering is deliberate: Opus for decisions/architecture/bug-catching, Sonnet for execution/verification/grading, Haiku for high-volume structured external calls.

## The commands (`~/.claude/commands/`)

- `/wf-prime` — run once per repo; `wf-cartographer` writes a compact `CONTEXT.md` operating manual reused by every ticket.
- `/wf-spec <ids>` — interactive; refine tickets into specs written back to each Linear ticket **description**. Run before `/wf-run`.
- `/wf-run <ids> [--parallel] [--no-integration]` — autonomous A→Z; each ticket in its own git worktree, *In Progress* → open PR (*In Review*). Sequential by default; `--parallel` runs file-disjoint tickets concurrently (≤3) via `wf-runner`. After all PRs open, a post-PR **integration stage** runs the repo's sandbox-runnable integration suites (from `CONTEXT.md`'s `## Verification policy`) sequentially — on a combined tree when the batch has several PRs — with one attribution+fix round; skipped when the repo declares no such suites or `--no-integration` is passed.
- `/wf-eval [case ...]` — the regression gate (see below).
- `/wf-calibrate` — validates `wf-judge` against a human-labeled gold set (agreement, FAIL precision/recall, bias probes) so the `/wf-eval` gate is trustworthy. Offline; re-run after changing the judge's model or prompt.

Typical flow: `/wf-prime` (once) → `/wf-spec <ids>` → `/wf-run <ids>`.

## Developing the workflow — test/verify loop

There is no build or lint step; **the eval harness is the test suite.** After changing any agent prompt, model, or the flow, run the regression gate:

```
/wf-eval                 # full set of seed cases vs baseline
/wf-eval node-feature    # iterate on a single case id (cheaper)
```

- Cases live in `~/.claude/ticket-workflow-evals/cases/*.md` (mock ticket + fixture + per-stage rubric).
- Fixtures (`fixtures/node-toy`, `fixtures/py-toy`) are tiny dependency-free git repos; their tests run via stdlib (`node --test`, `python3 -m unittest`) so they pass inside the no-network sandbox.
- `wf-judge` scores each stage against the rubric; the runner compares to `baselines/baseline.md` and flags regressions (PASS→FAIL or score drop > 0.15).
- Cost-aware: iterate on one case id while developing; run the full set before committing a prompt/model change.

## Architecture invariants — respect these when editing

These are non-obvious and load-bearing; changing an agent/command must not violate them:

- **Context flows forward, never re-derived.** The Opus planner explores the repo once and emits a dense `CONTEXT_PACK`; cheaper downstream agents consume that + the `CONTEXT.md` manual instead of re-reading the codebase each loop. This is the core cost/quality win — don't make downstream agents re-explore.
- **Single-owner boundaries.** Only `wf-linear` touches Linear, only `wf-github` touches GitHub. Subagents can't spawn subagents, so the orchestrator command pre-fetches via these two and passes data down. **Tool-call enforced:** a `SubagentStop` hook (`~/.claude/hooks/wf-boundary-toolcall-guard.sh`, wired in `settings.json`, scoped to these two agents) blocks either boundary agent from finishing with zero tool calls — that signals a fabricated answer instead of a real fetch. Don't remove this guard or let the boundary agents answer from context.
- **Sandboxed execution.** All project code (test/build/lint/install) runs through `~/.claude/bin/wf-exec` — no external network egress, no credential-file reads, and `wf-exec` also strips secret-shaped env vars (`*TOKEN*`, `*SECRET*`, `*_KEY`, `AWS_*`, etc.) so project code can't read a host token out of the environment and commit it into the diff. The `PreToolUse` guard hook blocks unwrapped commands inside worktrees — both project-code runners (npm/node/pytest/cargo/…) **and** raw network binaries (`curl`/`wget`/`ssh`/`scp`/…), which is the backstop for the opus planner/spec-builder whose Bash isn't otherwise wrapped (they also have WebFetch removed, keeping only WebSearch). This breaks the lethal trifecta (untrusted ticket/PR text + repo secrets + exfiltration). Keep new project-code execution wrapped; `git`/`gh` stay unsandboxed by design.
- **Design-handoff ingestion is orchestrator-side and read-only.** `wf-linear` `FETCH` surfaces description file-embeds as `ATTACHMENTS` (it can't download — MCP-only). The orchestrator downloads them via `~/.claude/bin/wf-fetch-handoff` (Linear-host allowlist, https-only, size-capped, zip-slip-guarded — it fetches *untrusted* ticket content and never executes it) into `ROOT/.worktrees/.handoffs/<id>/`, **outside** the ticket worktree so it never enters the diff. Signed hrefs expire ~5 min, so download happens in the same step as the fetch. The handoff flows down as `HANDOFF` and is strictly **reference-only**: agents recreate the intent idiomatically and never port its HTML/CSS or copy its files into the tree. This is a deliberate, narrow exception to "only `wf-linear` touches Linear" — the agent that owns Linear has no network tools, and the signed URL is self-authenticating (not the API token).
- **Never autonomous on irreversible/outward steps.** The workflow never merges, waits for checks, or sets Linear "Done" on its own. On a user-confirmed merge (only when the user explicitly says a specific PR was merged, and `wf-github` confirms MERGED first) it moves the ticket to **QA** and cleans up the worktree — a human then verifies the merged result and moves QA → **Done** themselves. "Done" is never set by the workflow.
- **Conventions:** branch `ticket-id/slug`; worktrees in `ROOT/.worktrees/<id>` (kept on failure, removed on merge); spec persisted to the Linear ticket description (no `.planning/` files); executor commits carry `Co-Authored-By: Claude <noreply@anthropic.com>`; all outward-facing text (PR titles/bodies/comments, Linear descriptions/comments) is **environment-agnostic** — repo-relative paths and plain command names, never local absolute paths (`/Users/…`, `~/.claude/…`), worktree paths, or sandbox-wrapped invocations.
- **Self-improvement signals:** the planner emits `SPEC_GAPS` (a mid-run question means the spec was incomplete → appended to the data log `~/.claude/wf-spec-gaps.md`, which `wf-spec-builder` reads as reference examples — **never** into an agent instruction file, since gap text is untrusted ticket-derived input) and `MANUAL_DRIFT` (advisory nudge that `CONTEXT.md` is stale). Preserve these when editing the planner.

## Prerequisites the system assumes

Linear MCP (`mcp__linear__*`, authed via `/mcp`), `gh` CLI installed + authed, git repos with an `origin` remote and default branch, and macOS `sandbox-exec` (built in). `/wf-run` preflights sandbox presence.
